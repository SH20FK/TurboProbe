# Проверка VPN для Интерсвязи — изменения и запуск

## Статус

Этот пакет изменяет исходники, но не публикует их в GitHub, GitHub Pages или Cloudflare. Проверки из Челябинска ещё не выполнялись. Число рабочих узлов и реальная совместимость с установленными версиями Xray/Mihomo должны быть подтверждены запуском на вашем ПК.

## Что исправлено

- Убраны синтетические задержки из агрегатора, Mihomo fallback и резервной загрузки сайта.
- TCP/DNS и ICMP Globalping больше не дают подтверждение работы VPN в РФ.
- Глубокий тест обязателен. При отсутствии Xray нельзя опубликовать TCP-пул как проверенный; без Mihomo соответствующие протоколы остаются непроверенными.
- Пинг в опубликованном JSON — медиана успешных HTTPS-запросов через туннель, а не TCP-пинг. Включает установление соединения, удалённый DNS, TLS и ответ цели.
- Для успеха нужны корректные ответы минимум двух из трёх независимых HTTPS-целей и полная загрузка 65536 байт через туннель. Сертификаты HTTPS проверяются; редиректы и HTML-заглушки не принимаются. Это строгая начальная политика: недоступность контрольных целей может привести к отклонению рабочего VPN.
- Каждый HTTPS-запрос использует новую SOCKS5h-сессию. Переменные HTTP_PROXY/HTTPS_PROXY/NO_PROXY не могут подменить маршрут. В конфигурации Xray маршрут по умолчанию — blackhole; в Mihomo — REJECT, слушатели закреплены за конкретными прокси.
- Полный конфиг, включая пароль, SNI, ключи и транспорт, участвует в идентификаторе. Успех другого конфига на том же адресе больше не переносится на этот конфиг.
- Старый кэш глубокой проверки больше не используется как свежий замер. Старые версии телеметрии и результаты старше часа не дают зелёный пинг.
- Worker не заменяет пустой результат фильтра первыми 20 узлами и не обходит фильтры через TXT-fallback.
- При нуле успешных проверок cloud-prober очищает основные и протокольные списки вместо сохранения прежних как новых.
- Сервисные признаки (ChatGPT, YouTube, Discord и др.) не угадываются по стране, протоколу или HTTP 403/404. Пока нет отдельных надёжных проверок сервиса, признаки остаются неизвестными, соответствующие сервисные списки пусты. Успешный тест туннеля не доказывает вход в аккаунт, проигрывание 4K или работу голосового UDP.

## 1. Установить изменения

Сначала создайте отдельную ветку и сохраните свои локальные изменения. Можно перенести изменённые исходники из ZIP или применить приложенный patch к версии, из которой был прислан архив:

```sh
git switch -c fix/strict-ru-probing
git apply --check /path/to/TurboProbe-ru-hardening.patch
git apply /path/to/TurboProbe-ru-hardening.patch
```

Patch проверяется относительно присланного ZIP; если ваша ветка с тех пор изменилась, конфликты нужно разрешать вручную. Пакет не содержит новой базы проверенных узлов.

## 2. Первый замер на вашем ПК (Windows)

Отключите другие VPN, TUN, системные прокси и маршрутизирующие приложения. ПК должен выходить в сеть напрямую через Интерсвязь. Проверяется страна RU и имя ISP/организации в HTTPS-ответе ipwho.is, до и после измерения. Домашний публичный IP в публикуемый JSON не записывается. Название города — заданная метка точки, не доказательство геолокации.

Из корня проекта:

```powershell
python -m pip install -r requirements.txt
$env:TP_XRAY_WORKERS = '2'
$env:TP_BATCH_SIZE = '6'
python tools/service_prober.py --vantage ru-local --limit 50 --batch-size 6 --timeout 5
```

Начните с 50 кандидатов. После проверки результата можно увеличить лимит. Xray/Mihomo используются из PATH или tools/bin, иначе старый механизм проекта пытается скачать их. Ошибка загрузки не подменяется вымышленным успехом. Версии ядер на ПК следует сверить с версиями в GitHub workflow; тестировавшийся здесь стенд не имел этих бинарников.

Результат — **sub/ru-verified.json**, схема 2. У каждого принятого узла есть checked_at, expires_at, ping_kind, verification_policy, идентификатор полного конфига и vantage_id=ru-chelyabinsk-intersvyaz. Глобальные списки этим запуском не изменяются.

Если геопроверка сообщает другую сеть, сначала проверьте другой VPN и провайдера. Если ipwho.is ошибается или недоступен, RU-публикация прервётся: не отключайте проверку и не ставьте ru_verified вручную.

## 3. Запуск через существующий self-hosted runner

В GitHub Settings → Actions → Runners добавьте **только вашему ПК на Интерсвязи** метку `ru-intersvyaz`. Workflow требует метки `[self-hosted, Windows, ru-intersvyaz]`; без неё задача останется в очереди. Убедитесь, что runner Online и на его учётной записи доступны Python и Git.

Запустите Actions → **RU-Vantage Verification** → Run workflow, сначала limit=50. Скрипт коммитит только sub/ru-verified.json в выбранную ветку. Ошибки процесса/установки/публикации не игнорируются. Не запускайте произвольные PR на домашнем self-hosted runner. Workflow оставлен ручным, расписание автоматически не включено.

Cloudflare endpoint ниже читает **main**. Результат, опубликованный в тестовую ветку, не появится в production до переноса в main. Не запускайте много параллельных замеров: начальные лимиты подобраны для снижения нагрузки на домашнюю сеть, а не для рекорда скорости проверки.

## 4. Строгая RU-подписка

После публикации исходников и свежего RU-снимка в main разверните обновлённый Worker. Важно развернуть **оба файла**: worker/index.js и worker/ru.js.

```sh
cd worker
npx wrangler@4 deploy
```

Новый маршрут после деплоя:

```text
https://sub.turboprobe.workers.dev/sub/ru-intersvyaz
https://sub.turboprobe.workers.dev/sub/ru-intersvyaz?format=base64
https://sub.turboprobe.workers.dev/sub/ru-intersvyaz?format=json
```

Поддерживаются только format=plain|base64|json и limit=1..5000. Неизвестные фильтры и Clash/Sing-box в этом специальном маршруте пока возвращают 400, а не молча изменяют смысл запроса. Используйте импорт URI/Base64 в клиенте; это сохраняет именно тот конфиг, который проверялся, без другой конвертации.

Worker проверяет схему, точку Интерсвязи, политику проверки, полный хеш конфига и время **каждого узла**. После часа, при пустом результате или недоступном источнике возвращает HTTP 503, без глобального fallback и без HTTP-кэширования ответа. Статический RU TXT намеренно не создаётся: выключенный ПК не может очистить уже опубликованный статический файл по истечении срока.

**Ограничение клиента:** многие VPN-клиенты сохраняют прежние узлы при ошибке обновления подписки. HTTP 503 запрещает серверу отдавать устаревшие узлы как свежие, но не удаляет уже импортированную копию из приложения. Для фактической доступности «прямо сейчас» включите URL-test/проверку соединения в клиенте; проверка сервера не гарантирует следующее подключение.

Для постоянной свежести нужен успешный новый замер и публикация чаще часа. На первом этапе запускайте вручную. Автоматическое расписание стоит включать только после измерения длительности, трафика и стабильности на вашем ПК.

## 5. Пересобрать сайт

В ZIP исходники интерфейса исправлены, но прежние собранные docs/assets сохранены — новая production-сборка в этом окружении не выполнялась (нет Vite/зависимостей и сетевого доступа к npm).

```sh
cd turboprobe-web
npm ci
npm run build
```

Сборка обновит docs/index.html и docs/assets. Опубликуйте их вместе с исходниками. До пересборки и публикации сайт продолжит выполнять старый JavaScript. Специальный RU-маршрут можно импортировать непосредственно в VPN-клиент: отдельная кнопка выбора провайдера на сайте в этом патче не добавлялась.

## Тесты и границы проверки

В локальном стенде выполнены:

```sh
python -m unittest tests.test_verification tests.test_parsers
node --test tests/test_ru_worker.mjs
python -m compileall -q tools
```

Результат: **27 Python-тестов и 9 Node-тестов прошли**. Сетевые ответы в регрессионных тестах подставные: проверяются правила принятия/отклонения, отказоустойчивость, полная передача данных, идентификаторы, TTL, пустая публикация, fallback и обработка старого кэша интерфейса. Это не измерения реальных VPN.

Полный существующий Python-набор в стенде не запускался успешно: тестам Telegram-прокси не хватает aiohttp; попытка установки заблокирована отсутствием сетевого доступа. Полная React/Vite-сборка, реальные Xray/Mihomo и сетевой тест из РФ здесь не выполнены. Новый workflow **Probe regression tests** устанавливает зависимости, запускает полный Python-набор, Node-тесты и production-сборку на GitHub-hosted runner; он не запускает сетевой перебор прокси.

### Приёмка на Интерсвязи

1. Убедиться, что RU workflow успешно завершился, а наблюдаемый провайдер соответствует Интерсвязи.
2. Проверить свежий JSON, взять несколько принятых URI и подключиться в своём клиенте из той же сети.
3. Проверить реальные нужные сайты и приложения — отдельно от лёгких контрольных HTTP-запросов.
4. Проверить отрицательный случай: заведомо неверный пароль/ключ не попадает в снимок.
5. После истечения часа без обновлений RU endpoint должен вернуть 503. Убедиться, как ваш клиент обрабатывает сохранённые узлы при этой ошибке.

Результат относится к конкретной точке и моменту проверки. Интерсвязь в Челябинске не является представителем всех операторов РФ; смена IP, нагрузки или фильтрации может изменить доступность сразу после измерения.
